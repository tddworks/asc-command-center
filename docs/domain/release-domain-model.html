Domain Model · Release

Four aggregates inside the Release context and how they reference each other — the most complex core context, worth its own zoom. ID references only, never embedded pointers. External aggregates from App Catalog and Xcode Cloud sit at the edges.

Where the drama is

AppStoreVersion is the core. It carries the state machine (PREPARE_FOR_SUBMISSION → WAITING_FOR_REVIEW → IN_REVIEW → …), the phased-release plan, and the release type. Everything in Release revolves around moving a Version through this machine.

Why ReviewSubmission is peer, not child

The modern ReviewSubmission is a batch — it can bundle a Version plus IAPs, in-app events, and custom product pages into one review. Modelling it as a child of AppStoreVersion would hide this batch-across-aggregates structure. It's a peer aggregate that references the version(s) it submits.

Build as independent aggregate

Build has its own lifecycle (uploaded → processed → usable → expired) that is not owned by any single Version. The same Build binary can be attached to an App Store Version and distributed by multiple BetaGroups — each with its own 90-day TestFlight clock. Hence a peer, not a child.
